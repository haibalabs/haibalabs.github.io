# Releases

Reviewed data that every visitor sees, kept beside the world dataset (`canonical-t2.json`, the default) rather than in it. Adding records here publishes them on the next deploy, so each change to these files is a release decision for Rachid, after Atlas's technical acceptance and Iris's review of the images.

## released-images-v1.json

World-event images whose association with their event was reviewed and accepted for release. It holds 794 images for 794 events: the 61 first released plus 733 from Iris's continued image review, combined by Atlas's export (history-dp PR 40, `combine_image_exports.py`) and corrected by PR 41 (legacy-bound SHA256 `2b492070…`), then rebound to the canonical file through event IDs and record fingerprints (SHA256 `d4387b30…`). The reviewed exceptions still apply (Vancouver excluded; the Clement VIII image recorded as a site), the 1900 Paris poster is now a symbol, the Edward II marriage image (a 2023 monument) is a site, and five credits no longer carry leaked Wikimedia page styling. Round 2 adds 722 images from the resumed image review, combined by history-dp PR 49 and accepted by Iris (SHA256 `6f53fe8d…`), for 1,516 images on 1,516 events; the 794 earlier records are unchanged byte for byte. The caption rewrite (T5-CAPTION-BACKLOG, Rachid 2026-10-27) then replaced 939 captions with ones that describe what the image shows, with no negations or dates, and added a reviewed `display_date` to 951 records (136 of them an explicit null). Iris produced it under the v2 caption policy and Atlas accepted it (SHA256 `366b2e03…`). Only `caption` and `display_date` changed. A second pass (history-dp PR 58) re-checked the guard's holds against the saved responses with narrower guards, adding 193 caption rewrites and 195 reviewed display dates (38 of them null), again accepted by Atlas (SHA256 `474f32d5…`). A third batch then covered the 365 remaining clean proposals, adding 363 caption rewrites and 365 reviewed display dates. Atlas accepted it on a uniform random audit of 50 against the saved sources: none wrong, 2 unresolved, both corrected along with two date conflicts found by a targeted check (SHA256 `affb311e…`). Five records stay held: two unanswered requests, two source conflicts and one over-length caption. Round 3 adds 234 images for events that had none, from Iris's 582-event review under the v2 caption policy. Each addition carries a reviewed `display_date`. Atlas accepted them on a uniform random audit of 50 against the saved sources (none wrong, 1 unresolved), with 8 candidates held (SHA256 `e469489b…`). That makes 1,750 images on 1,750 events. The 1,516 earlier records keep the same values; only the position of `display_date` within each record changed. Twenty-three of the events have open data-issue references, and their viewer says details are still being reviewed. The early-times release adds the timeline's 15 opening events, from the Big Bang to the Cambrian, with one image each. Round 4 adds 62 images for events that had none, from Iris's continued image review under the v2 caption policy, each with a reviewed `display_date` (18 of them null). The earlier records keep their values, and the 1,750 before early-times are unchanged byte for byte. - Credits come from source metadata and some run to thousands of characters; the viewer shows the first 280, ending at a word, with the full text on hover and on the source page (`shortCredit` in `modules/world-images.js`).

- `source.events_sha256` is the hash of the data file the records are bound to: `canonical-t2.json` (`49b8f43b…`). `prior_events_sha256` names the legacy `events.json` they were first reviewed against. `records` are the sidecar export's records unchanged. Each record's `record_index` is its event's position in that file, and `baseline_record_sha256` is the SHA256 of that record as Python's `json.dumps(record, sort_keys=True, ensure_ascii=False)` writes it; `evidence_event_id` is its canonical ID, for cross-reference only.
- The site loads this file with the events and attaches all records or none: the loaded bytes must have `events_sha256`, positions must be valid and unique, and every target event must still be that file's record. If anything differs, for example after the data file is regenerated, or on `?file=events.json`, visitors see no world images and the reason goes to the browser console. Rebind the records to the new file before deploying it.
- Records carry the display fields of the review: image and source URLs, role, caption, credit, license and rights statement, the image's date (`image_date`, or a cleaned `display_date` when the export supplies one) and, as review evidence, `date_qualification` where the image is not a photo of the event at its time. The card shows the photo and a one-line caption; clicking it opens the full-window viewer with the caption, the image's date with no label, and a small (i) button that shows the credit, license and source links. The date note is not shown, and a trailing "Image date: …" is dropped from a caption (Rachid, 2026-10-26). A reviewed `display_date` is shown as written, and an explicit `display_date: null` shows no date. Without that field, the viewer summarizes `image_date` (`displayDate` in `modules/world-images.js`): a full ISO date as is, and a date in a known shape as its year or century, keeping its era, "c.", "before", "after" and ranges. Upload dates, signature timestamps and anything it can't safely summarize (an unknown date with an editing date, "1945 or later years" in German, a dynasty) show no date rather than a year that changes the meaning (Iris's review of PR 25). On the current release, 378 images show a full date, 253 a year, 90 another form and 73 nothing.
- Roles (`IMAGE_ROLES` in `modules/world-images.js`): `event_photo`, `event_aftermath`, `portrait`, `site`, `map`, `symbol`, `retrospective_illustration` and `scientific_context` (a modern observation or specimen photo that is evidence for an early event, such as a fossil). The viewer shows no role label (Rachid, 2026-10-26); the caption and the image's date say what the image is and when. The export maps the review's `contemporary_event` to `event_photo` and `aftermath` to `event_aftermath`. Any other role, including `unknown`, keeps the whole release off; every role other than the first two needs a `date_qualification`.
- One image per event, with no gallery (Rachid, 2026-10-25): a release chooses a single image for each event, and a repeated position is refused.

To withdraw a release, remove its records (or revert the commit that added them); events and user data are unaffected. `tests/unit/world-images.test.js` checks every record against `canonical-t2.json`.

## released-locations-v1.json

Accepted location batches, exported by history-dp `location_sidecar.py` (format and rules in its `docs/location-sidecar.md`). Release 1 updates 2,260 locations across 2,252 events, including 1,054 events gaining a map point and no events losing all points. Hermes exported the accepted batch and rebound it to the current canonical file; Atlas accepted both the original quality result and the scoped rebind. The frozen 50-case audit recorded one error and no unresolved cases (2%); this is an operational sample result, not a population-error guarantee. Fort Matanzas and the frozen event-pair holds remain excluded.

The release file is copied byte for byte from data revision `811b28a761ca1039982dcdab2274a53a53aa595e`, `pilots/t7-location-acceptance-v2/release-01-rebind-49b8f43b/released-locations-v1.json`, SHA256 `c95f48ee0b46b9a77480aadaadf3126d906c7929520d2faf8b97c0083ef32209`. Its quality tally is `777b6abbdd8b5cc1609962e1878df713ab2a4aa815eb414b828da0fae13196f2`. The canonical events and 1,765 released images are unchanged. These are release contents; actual publication requires the merged deployment and a live receipt.

- `source.events_sha256` binds the file to `canonical-t2.json` (`49b8f43b…`). Each record names an event by `record_index` and `event_id`, and lists the event locations it changes: each gets a new `place_id` (different when duplicate places were merged) and that place's reviewed geography from `places`.
- The site applies all records or none (`modules/world-locations.js`): the loaded bytes must have `events_sha256`, positions must be valid and unique, and each target event must still be that file's record, with the same ID, name, date and location identity, not personal, edited or synced. Places must be `resolved` with valid coordinates and a known precision (`site`, `settlement`, `region`, `country`, `polity`, `approximate`). If anything differs, no location changes and the reason goes to the browser console. The browser relies on the byte hash for record and location fingerprints (`baseline_record_sha256`, `before_sha256`); `tests/unit/world-locations.test.js` checks those fingerprints.
- Locations are applied after the released images, and image checks compare each event's places as loaded, so a merged place never turns an image off.
- The map shows a point for a `resolved` place, as for `reused` and `corrected`; anything less precise than `site` counts as approximate in the map's area filter. The location's tooltip says "Reviewed location" with its precision. A manual correction from the site's own corrections file still takes precedence: a location whose manual point differs from its released place keeps its loaded values (reported in the console), so the map never labels the manual point with the release's precision; one whose manual point agrees is updated.

To withdraw a release, empty its records or revert the commit that added them; the events' own locations come back.
