# Releases

Reviewed data that every visitor sees, kept beside the world dataset (`canonical-t2.json`, the default) rather than in it. Adding records here publishes them on the next deploy, so each change to these files is a release decision for Rachid, after Atlas's technical acceptance and Iris's review of the images.

## released-images-v1.json

World-event images whose association with their event was reviewed and accepted for release. It holds 794 images for 794 events: the 61 first released plus 733 from Iris's continued image review, combined by Atlas's export (history-dp PR 40, `combine_image_exports.py`) and corrected by PR 41 (legacy-bound SHA256 `2b492070…`), then rebound to the canonical file through event IDs and record fingerprints (SHA256 `d4387b30…`). The reviewed exceptions still apply (Vancouver excluded; the Clement VIII image recorded as a site), the 1900 Paris poster is now a symbol, the Edward II marriage image (a 2023 monument) is a site, and five credits no longer carry leaked Wikimedia page styling. Seventeen of the events have open data-issue references, and their viewer says details are still being reviewed.
- Credits come from source metadata and some run to thousands of characters; the viewer shows the first 280, ending at a word, with the full text on hover and on the source page (`shortCredit` in `modules/world-images.js`).

- `source.events_sha256` is the hash of the data file the records are bound to: `canonical-t2.json` (`4160e58f…`). `prior_events_sha256` names the legacy `events.json` they were first reviewed against. `records` are the sidecar export's records unchanged. Each record's `record_index` is its event's position in that file, and `baseline_record_sha256` is the SHA256 of that record as Python's `json.dumps(record, sort_keys=True, ensure_ascii=False)` writes it; `evidence_event_id` is its canonical ID, for cross-reference only.
- The site loads this file with the events and attaches all records or none, with the same checks as the admin preview (`previews/README.md`): the loaded bytes must have `events_sha256`, positions must be valid and unique, and every target event must still be that file's record. If anything differs, for example after the data file is regenerated, or on `?file=events.json`, visitors see no world images and the reason goes to the browser console. Rebind the records to the new file before deploying it.
- Records carry the display fields of the review: image and source URLs, role, caption, credit, license and rights statement, and `date_qualification` where the image is not a photo of the event at its time. The card shows the photo and a one-line caption; clicking it opens the full-window viewer with the caption and date qualification, and a small (i) button that shows the credit, license and source links.
- Roles (`IMAGE_ROLES` in `modules/world-images.js`): `event_photo`, `event_aftermath`, `portrait`, `site`, `map`, `symbol` and `retrospective_illustration`. The viewer shows no role label (Rachid, 2026-10-26); the caption and date qualification say what the image is and when. The export maps the review's `contemporary_event` to `event_photo` and `aftermath` to `event_aftermath`. Any other role, including `unknown`, keeps the whole release off; every role other than the first two needs a `date_qualification`.
- One image per event, with no gallery (Rachid, 2026-10-25): a release chooses a single image for each event, and a repeated position is refused.
- The admin preview replaces these images while it is on.

To withdraw a release, remove its records (or revert the commit that added them); events and user data are unaffected. `tests/unit/world-images.test.js` checks every record against `canonical-t2.json`.

## released-locations-v1.json

Accepted location batches, exported by history-dp `location_sidecar.py` (format and rules in its `docs/location-sidecar.md`). It currently holds no records, so every event shows its own locations.

- `source.events_sha256` binds the file to `canonical-t2.json` (`4160e58f…`). Each record names an event by `record_index` and `event_id`, and lists the event locations it changes: each gets a new `place_id` (different when duplicate places were merged) and that place's reviewed geography from `places`.
- The site applies all records or none (`modules/world-locations.js`): the loaded bytes must have `events_sha256`, positions must be valid and unique, and each target event must still be that file's record, with the same ID, name, date and location identity, not personal, edited or synced. Places must be `resolved` with valid coordinates and a known precision (`site`, `settlement`, `region`, `country`, `polity`, `approximate`). If anything differs, no location changes and the reason goes to the browser console. The browser relies on the byte hash for record and location fingerprints (`baseline_record_sha256`, `before_sha256`); `tests/unit/world-locations.test.js` checks those fingerprints.
- Locations are applied after the released images, and image checks compare each event's places as loaded, so a merged place never turns an image off.
- The map shows a point for a `resolved` place, as for `reused` and `corrected`; anything less precise than `site` counts as approximate in the map's area filter. The location's tooltip says "Reviewed location" with its precision. A manual correction from the site's own corrections file still takes precedence: a location whose manual point differs from its released place keeps its loaded values (reported in the console), so the map never labels the manual point with the release's precision; one whose manual point agrees is updated.

To withdraw a release, empty its records or revert the commit that added them; the events' own locations come back.
